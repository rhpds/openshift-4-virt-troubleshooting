== Overview & Objectives

This lab focuses on diagnosing and resolving Virtual Machine networking and external exposure issues in OpenShift Virtualization. By the end of this module, you will:

* Troubleshoot secondary network attachment failures involving CNI and Multus `NetworkAttachmentDefinition` objects.
* Diagnose and repair external HTTP routing failures (`Route` → `Service` → `Pod`) for applications hosted inside a Virtual Machine.

[NOTE]
====
This lab is designed to give you hands-on experience with real-world scenarios. We highly recommend exploring the errors, running the diagnostic commands, and trying to fix the issues on your own first—that is where the best learning happens!

If you get stuck or want to verify your findings, the companion *Guided Solution* is always available to help guide you through the next steps.
====

== Tasks

=== Task 1: Troubleshooting Failure Scenario A

==== Problem Scenario
A Virtual Machine named `vm3` is configured with a secondary network interface in the namespace `{user}-troubleshoot-02`.

When attempting to start `vm3`, the Virtual Machine never reaches a `Running` state and remains stuck during pod initialization.

Run the following commands to verify the current non-running state of `vm3`:
[source,sh,subs="attributes+"]
----
oc get vm,vmi vm3 -n {user}-troubleshoot-02
oc get pods -n {user}-troubleshoot-02
----

The terminal output should look similar to this:

.Terminal output confirming `vm3` is stuck during startup
image::vm3-1.png[Terminal output of oc get vm,vmi and pods showing vm3 stuck before Running, align="center"]

==== Reference Documentation
* Consult the Red Hat documentation on link:https://redhat.com[Attaching a virtual machine to a Linux bridge network^].

==== Goal
Investigate the cluster components and network attachment configuration, determine why the secondary interface cannot initialize, implement a fix, and transition `vm3` to a `Running` state.

=== Task 2: Troubleshooting Failure Scenario B

==== Problem Scenario
A Virtual Machine named `vm4` is deployed in the namespace `{user}-troubleshoot-02` and runs a web server exposed externally via an OpenShift `Route` (`vm4-web-route`)

Although `vm4` reports a `Running` state, users attempting to access the application through the `Route` URL receive a `503 Service Unavailable` (`Application is not available`) response.

Run the following commands to verify that `vm4` is running and test external HTTP access via `vm4-web-route`:
[source,sh,subs="attributes+"]
----
oc get vm,vmi vm4 -n {user}-troubleshoot-02
ROUTE_URL=$(oc get route vm4-web-route -n {user}-troubleshoot-02 -o jsonpath='{.spec.host}')
curl -i http://$ROUTE_URL
----

The terminal output should look similar to this:

.Terminal output showing `vm4` is `Running` while `curl` to `vm4-web-route` returns `503 Service Unavailable`
image::vm4-1.png[Terminal output showing vm4 Running and curl returning 503 Application is not available, align="center"]

==== Reference Documentation
* Consult the Red Hat documentation on link:https://redhat.com[Exposing a virtual machine by using a Service^].

==== Goal
Trace the routing chain (`Route` → `Service` → `Endpoints` → `Pod`), pinpoint why traffic is not reaching `vm4`, implement a fix, and verify that `curl http://$ROUTE_URL` returns the web page hosted on `vm4`.

== Suggested Troubleshooting Reference Workflow

Use the following commands in sequence to analyze the state of either Virtual Machine (`vm3` or `vm4`) and isolate the root cause of the networking failures:

Check high-level VM and VMI states:
[source,sh,subs="attributes+"]
----
oc get vm,vmi -n {user}-troubleshoot-02
----

Locate underlying `virt-launcher` pods and inspect their labels:
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-02 --show-labels
----

Describe a `virt-launcher` pod to view CNI and sandbox events (replace `<virt-launcher-pod>` with the pod ID found above):
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod> -n {user}-troubleshoot-02
----

Inspect `NetworkAttachmentDefinition` objects in the namespace:
[source,sh,subs="attributes+"]
----
oc get net-attach-def -n {user}-troubleshoot-02 -o yaml
----

Inspect `Route`, `Service`, and `Endpoints` objects to trace external traffic routing:
[source,sh,subs="attributes+"]
----
oc get route,svc,endpoints -n {user}-troubleshoot-02
oc describe svc vm4-web-svc -n {user}-troubleshoot-02
----
