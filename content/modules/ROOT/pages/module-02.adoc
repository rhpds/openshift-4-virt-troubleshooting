== Overview & Objectives

This lab focuses on diagnosing and resolving advanced networking and scheduling faults within OpenShift Virtualization. By the end of this module, you will:

- Identify and resolve Layer 2 Container Network Interface (CNI) attachment failures.
- Correct pod scheduling errors caused by invalid hardware resource requests.
- Troubleshoot and fix Layer 3 routing anomalies injected via Cloud-Init.

[NOTE]
====
This lab is designed to give you hands-on experience with real-world scenarios. We highly recommend exploring the errors, running the diagnostic commands, and trying to fix the issues on your own first—that is where the best learning happens! 

If you get stuck or want to verify your findings, the companion *Guided Solution* is always available to help guide you through the next steps.
====

== Tasks

=== Task 1: Troubleshooting CNI and Network Attachment (Layer 2 Fault)

==== Problem Scenario
A Virtual Machine named `vm3` is deployed in the namespace `{user}-troubleshoot-02` but fails to start. 

The VM's underlying orchestration pod is unable to initialize because it cannot bind to the requested secondary network. A configuration error in the cluster's network attachment definition is causing a physical hardware collision.

==== Reference Documentation & Setup
- Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.14/html/virtualization/virtual-machine-networking#virt-connecting-vm-to-linux-bridge[Connecting a virtual machine to a Linux bridge network^].
- The VM relies on a custom NetworkAttachmentDefinition named `vm-private-net`.

==== Goal
Investigate the cluster's network definitions to determine why the secondary network attachment is failing. Modify the definition to use the correct Linux bridge topology so that `vm3` can successfully transition to a `Running` state.

=== Task 2: Troubleshooting Scheduling and Layer 3 Routing (Double Fault)

==== Problem Scenario
A second Virtual Machine named `vm4` is deployed in the same namespace but remains stuck in a `Pending` state. The scheduler refuses to assign the workload to a node due to a mismatch in the requested network interface hardware.

Furthermore, once the hardware request is corrected and the VM boots, it still lacks network connectivity. An error in the Cloud-Init configuration has injected a mathematically isolated subnet mask into the Guest OS, preventing traffic routing.

==== Reference Documentation & Setup
- Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.14/html/virtualization/virtual-machine-networking#virt-configuring-sriov-net-for-vms[Configuring SR-IOV networks for virtual machines^].
- Review Cloud-Init network configuration best practices for static IP injection.

==== Goal
Diagnose the scheduling error on `vm4` and correct the interface hardware binding in the YAML spec. After the VM boots, access the Guest OS, identify the improper subnet mask scoped to the secondary network interface, and update the Cloud-Init script to apply the correct `/24` subnet mask without altering the dynamically generated IP.

== Suggested Troubleshooting Reference Workflow

Use the following commands to navigate the cluster objects, inspect network definitions, and verify the Guest OS configuration.

Check the high-level VM and VMI states in your namespace:
[source,sh,subs="attributes+"]
----
oc get vm -n {user}-troubleshoot-02
oc get vmi -n {user}-troubleshoot-02
----

Identify the underlying virt-launcher pods:
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-02
----

Describe a specific virt-launcher pod to uncover scheduling or CNI initialization errors (replace `<virt-launcher-pod>` with the target pod name):
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod> -n {user}-troubleshoot-02
----

Inspect the custom NetworkAttachmentDefinition causing the Layer 2 fault:
[source,sh,subs="attributes+"]
----
oc get networkattachmentdefinition -n {user}-troubleshoot-02
oc describe networkattachmentdefinition vm-private-net -n {user}-troubleshoot-02
----

Review and edit the VM configuration to fix hardware binding errors:
[source,sh,subs="attributes+"]
----
oc get vm vm4 -o yaml -n {user}-troubleshoot-02
----

Access the Guest OS console once a VM is running (Username: `cloud-user` / Password: `password123`):
[source,sh,subs="attributes+"]
----
virtctl console vm4 -n {user}-troubleshoot-02
----

Verify the network configuration applied by Cloud-Init inside the Guest OS:
[source,sh,subs="attributes+"]
----
ip a show eth1
----
