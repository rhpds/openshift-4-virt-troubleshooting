== Overview & Objectives

This lab focuses on diagnosing and resolving Containerized Data Importer (CDI) storage and DataVolume provisioning issues in OpenShift Virtualization. By the end of this module, you will:

* Understand how CDI clones and provisions boot volumes from `DataSource` templates via `DataVolumeTemplates`.
* Diagnose and resolve DataVolume issues and cross-namespace `DataSource` reference errors.

[NOTE]
====
This lab is designed to give you hands-on experience with real-world scenarios. We highly recommend exploring the errors, running the diagnostic commands, and trying to fix the issues on your own first—that is where the best learning happens! 

If you get stuck or want to verify your findings, the companion *Guided Solution* is always available to help guide you through the next steps.
====

== Tasks

=== Task 1: Troubleshooting Failure Scenario A

==== Problem Scenario
A Virtual Machine named `vm8` is configured to provision its root disk from a golden `DataSource` using a `DataVolumeTemplate` inside the namespace `{user}-troubleshoot-05`.

When attempting to start the VM, the startup process stalls during storage provisioning, preventing the workload instance from launching.

Run the following command to verify the current non-running state of `vm8`:
[source,sh,subs="attributes+"]
----
oc get vm vm8 -n {user}-troubleshoot-05
----

The output should look similar to this:

[source,texinfo]
----
NAME   AGE   STATUS         READY
vm8    20h   Provisioning   False
----

==== Reference Documentation & Setup
* Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/virtualization/storage#dv-configuration-tasks[Data volumes in OpenShift Virtualization^].
* Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/virtualization/storage#virt-enabling-user-permissions-to-clone-datavolumes[Enabling user permissions to clone data volumes across namespaces^].

==== Goal
Investigate the DataVolume and CDI events, determine why the storage provisioning is failing, patch the Virtual Machine configuration to resolve the issue, and transition `vm8` to a `Running` state.

=== Task 2: Troubleshooting Failure Scenario B

==== Problem Scenario
A Virtual Machine named `vm9` fails to provision its boot disk in the namespace `{user}-troubleshoot-05`.

The VM is configured with an instance type and preference to clone a shared golden image (`centos9-golden`) in openshift namespace, but the DataVolume is never created.

Run the following command to verify the current non-running state of `vm9`:
[source,sh,subs="attributes+"]
----
oc get vm vm9 -n {user}-troubleshoot-05
----

The output should look similar to this:

[source,texinfo]
----
NAME   AGE   STATUS         READY
vm9    20h   Stopped        False
----

[NOTE]
====
Unlike `vm8`, `vm9` never enters the `Provisioning` state: the VirtualMachine controller fails before any DataVolume is created, so the VM reports `Stopped` with a `Failure` condition.
====

==== Goal
Inspect the DataVolume and Virtual Machine specifications, pinpoint why CDI cannot locate the source image template, update the VM definition, and restore `vm9` to a `Running` state.

== Suggested Troubleshooting Reference Workflow

Use the following commands in sequence to analyze the state of either Virtual Machine (`vm8` or `vm9`) and isolate the root cause of the CDI storage failures:

Check high-level VM states:
[source,sh,subs="attributes+"]
----
oc get vm -n {user}-troubleshoot-05
----

Check DataVolumes and PersistentVolumeClaims:
[source,sh,subs="attributes+"]
----
oc get dv,pvc -n {user}-troubleshoot-05
----

Inspect a specific DataVolume and its CDI condition messages (replace `<dv-name>` with the DataVolume name):
[source,sh,subs="attributes+"]
----
oc describe dv <dv-name> -n {user}-troubleshoot-05
----

Inspect the Virtual Machine specification (replace `<vm-name>` with `vm8` or `vm9`):
[source,sh,subs="attributes+"]
----
oc get vm <vm-name> -n {user}-troubleshoot-05 -o yaml
----

Check for any importer or clone pods in the namespace:
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-05
----

Query cluster events sorted chronologically:
[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-05 --sort-by='.metadata.creationTimestamp'
----
