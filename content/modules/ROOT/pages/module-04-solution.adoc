== Overview

This is the companion solution guide for Lab 4. It walks through the exact steps to reproduce and resolve both Live Migration faults for `vm6` and `vm7`. Each step shows the CLI command and, where useful, the equivalent OpenShift Web Console action.

== Task 1 Solution: Troubleshooting Quota-Blocked Migrations

=== Step 1: Start the live migration

Start a live migration of `vm6`:

[source,sh,subs="attributes+"]
----
virtctl migrate vm6 -n {user}-troubleshoot-04
----

_Web Console:_ *Virtualization -> VirtualMachines -> vm6 -> Actions -> Migrate*.

_Observation:_ The command is accepted, but the migration does not complete. It stays in `Preparing` (the console shows *Preparing for migration*).

=== Step 2: Confirm the migration is stuck

Check the migration object and the VM's current node:

[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm6 -n {user}-troubleshoot-04
----

_Observation:_ A `VirtualMachineInstanceMigration` object exists but its `PHASE` is not `Succeeded`, and `vm6` is still `Running` on its original node. Note the `NODENAME` before continuing so you can compare it later.

=== Step 3: Find the rejected target pod

Filter the namespace events for the quota rejection:

[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --sort-by='.lastTimestamp' | grep -i -E 'FailedCreate|quota'
----

_Observation:_ You will see a warning like:

[source,text]
----
Warning  FailedCreate  ...  Error creating pod: pods "virt-launcher-vm6-..." is forbidden: exceeded quota: migration-quota, requested: requests.memory=..., used: ..., limited: 3000Mi
----

The event appears even though `oc get pods` never shows the target pod: Kubernetes rejects the pod before it is created.

=== Step 4: Root cause

A live migration starts a temporary second `virt-launcher` pod on the target node. That pod must fit inside the namespace `ResourceQuota` `migration-quota`, which limits `requests.memory` to `3000Mi`. `vm6` alone already consumes most of that budget, so the target pod is rejected and the migration waits indefinitely.

_Web Console:_

. Navigate to *Home -> Events* (or *Administration -> Events*).
. Set the Project to `{user}-troubleshoot-04`.
. Look for the `FailedCreate` warning that mentions `migration-quota`.

=== Step 5: Remove the quota

Your tenant user has been granted the `quota-admin` role in this namespace:

[source,sh,subs="attributes+"]
----
oc delete resourcequota migration-quota -n {user}-troubleshoot-04
----

_Web Console:_

. Navigate to *Administration -> ResourceQuotas*.
. Select the `{user}-troubleshoot-04` project.
. Open the options menu next to `migration-quota` and choose *Delete ResourceQuota*.

_Observation:_ The command returns `resourcequota "migration-quota" deleted`.

=== Step 6: Verify the migration completes

[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm6 -n {user}-troubleshoot-04
----

_Observation:_ The migration reaches `Succeeded` and `vm6` is `Running` on a different node than the one you noted in Step 2. The target pod is created automatically and the migration resumes; no restart is required. If it has not resumed after a few minutes, re-run `virtctl migrate vm6 -n {user}-troubleshoot-04`.

== Task 2 Solution: Troubleshooting Scheduling Conflicts

=== Step 1: Make sure vm7 is running

The `migration-quota` also blocked `vm7`'s first pod, so `vm7` may still be `Starting` after Task 1. Check:

[source,sh,subs="attributes+"]
----
oc get vm vm7 -n {user}-troubleshoot-04
oc get vmi vm7 -n {user}-troubleshoot-04
----

_Observation:_ While the quota blocks it, the VMI stays `Pending` and no `virt-launcher-vm7-*` pod is ever created: the VMI itself is not a pod, so it is accepted, but the launcher pod is rejected at creation by quota admission. If `vm7` is still `Starting` after Task 1, restart it:

[source,sh,subs="attributes+"]
----
virtctl restart vm7 -n {user}-troubleshoot-04
----

Wait until `oc get vmi vm7 -n {user}-troubleshoot-04` reports `Running` before continuing.

=== Step 2: Start the migration

[source,sh,subs="attributes+"]
----
virtctl migrate vm7 -n {user}-troubleshoot-04
----

_Web Console:_ *Virtualization -> VirtualMachines -> vm7 -> Actions -> Migrate*.

_Observation:_ The migration is accepted and moves to `Migrating`, then stalls indefinitely.

=== Step 3: Find the pending target pod

[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04 | grep virt-launcher-vm7
----

_Observation:_ There are two pods: the original `Running` pod and a new `virt-launcher-vm7-...` pod stuck in `Pending`.

=== Step 4: Read the scheduler event

Describe the pending pod and filter for the scheduling failure:

[source,sh,subs="attributes+"]
----
oc describe pod <pending-virt-launcher-vm7-pod> -n {user}-troubleshoot-04 | grep -A5 -i FailedScheduling
----

Or filter the namespace events directly:

[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --sort-by='.lastTimestamp' | grep -i -E 'FailedScheduling|affinity'
----

_Observation:_ The scheduler reports:

[source,text]
----
Warning  FailedScheduling  ...  0/X nodes are available: X node(s) didn't match pod affinity rules.
----

_Web Console:_

. Navigate to *Workloads -> Pods*.
. Open the pending `virt-launcher-vm7-...` pod.
. Check the *Events* tab.

=== Step 5: Cancel the stuck migration

[source,sh,subs="attributes+"]
----
virtctl migrate-cancel vm7 -n {user}-troubleshoot-04
----

_Web Console:_ *Virtualization -> VirtualMachines -> vm7 -> Actions -> Cancel Migration*.

_Observation:_ The `VirtualMachineInstanceMigration` object is removed and the pending target pod disappears.

=== Step 6: Remove the strict affinity rule

The VM template requires `vm7` to run on the same node as the pod labeled `app: anchor`, which makes migration to another node impossible. Edit the VM:

[source,sh,subs="attributes+"]
----
oc edit vm vm7 -n {user}-troubleshoot-04
----

In `spec.template.spec`, delete the whole `affinity` block:

[source,yaml]
----
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: anchor
              topologyKey: kubernetes.io/hostname
----

Save and exit. Alternatively, remove it non-interactively:

[source,sh,subs="attributes+"]
----
oc patch vm vm7 --type=merge -p '{"spec":{"template":{"spec":{"affinity":null}}}}'
----

_Web Console:_

. Navigate to *Virtualization -> VirtualMachines* and open `vm7`.
. Switch to the *YAML* tab.
. Delete the `affinity` block and click *Save*.

_Observation:_ The change is applied to the running VMI as well, so a restart is not required. Confirm with:

[source,sh,subs="attributes+"]
----
oc get vmi vm7 -n {user}-troubleshoot-04 -o jsonpath='{.spec.affinity}{"\n"}'
----

The command returns an empty line.

=== Step 7: Migrate again and verify

[source,sh,subs="attributes+"]
----
virtctl migrate vm7 -n {user}-troubleshoot-04
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm7 -n {user}-troubleshoot-04
----

_Observation:_ The migration reaches `Succeeded` and `vm7` remains `Running`, now on a different node. Because the strict affinity rule is gone, the scheduler can place the target pod on any node that satisfies the VM's remaining requirements.
