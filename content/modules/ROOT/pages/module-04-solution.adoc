== Solution for Task 1: Troubleshooting Failure Scenario A

==== Guided Investigation & Root Cause Analysis

. Initiate a live migration for `vm6`:
+
[source,sh,subs="attributes+"]
----
virtctl migrate vm6 -n {user}-troubleshoot-04
----
+
[TIP]
====
In the OpenShift Web Console, navigate to *Virtualization* → *VirtualMachines* → *vm6* → *Actions* → *Migrate*.
====
+
_Observation:_ The migration request is accepted, but it remains stuck in the `Preparing` phase (displayed as *Preparing for migration* in the Web Console).

. Inspect the migration object and record the current `NODENAME` of `vm6`:
+
[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm6 -n {user}-troubleshoot-04
----
+
_Observation:_ A `VirtualMachineInstanceMigration` object exists, but its `PHASE` never reaches `Succeeded`, and `vm6` remains `Running` on its original node.

. Check the pods in the namespace to see if a target migration pod was created:
+
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04
----
+
_Observation:_ Only the original `virt-launcher-vm6` pod is listed; no second target pod exists.

. Query the recent namespace warning events to find out why the target pod was not created:
+
[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --field-selector type=Warning --sort-by='.lastTimestamp'
----
+
_Observation:_ At the bottom of the output, the event log reports a `FailedCreate` warning:
+
[source,text]
----
Warning  FailedCreate  ...  Error creating pod: pods "virt-launcher-vm6-..." is forbidden: exceeded quota: migration-quota, requested: requests.memory=..., used: ..., limited: 3500Mi
----
+
.Terminal output showing `FailedCreate` warning due to `migration-quota` memory limit
image::vm6-1-sol.png[Terminal output of oc get events showing FailedCreate exceeded quota migration-quota, align="center"]

. *Root Cause Analysis (RCA):* A live migration requires spinning up a temporary second `virt-launcher` pod on the destination node before transferring memory state. Because the namespace `ResourceQuota` (`migration-quota`) caps total `requests.memory` at `3500Mi`—which is already consumes—Kubernetes admission control rejects the target pod before it is created, causing the migration to stall indefinitely.

==== Step-by-Step Resolution

. Inspect the current `migration-quota` configuration to see its existing limits and usage:
+
[source,sh,subs="attributes+"]
----
oc describe resourcequota migration-quota -n {user}-troubleshoot-04
----

. Increase the `requests.memory` limit by 6Gi (from `3500Mi` to 6Gi`) so the namespace has enough headroom for both VMs and their temporary migration pods:
+
[source,sh,subs="attributes+"]
----
oc patch resourcequota migration-quota -n {user}-troubleshoot-04 --type=merge -p '{"spec":{"hard":{"requests.memory":"6Gi"}}}'
----
+
[TIP]
====
Alternatively, run `oc edit resourcequota migration-quota -n {user}-troubleshoot-04` (or navigate to *Administration* → *ResourceQuotas* → *migration-quota* → *YAML* in the OpenShift Web Console) and update `spec.hard.requests.memory` to `6Gi`.
====

. Verify that the updated quota limits are active:
+
[source,sh,subs="attributes+"]
----
oc describe resourcequota migration-quota -n {user}-troubleshoot-04
----

. Verify that the migration automatically resumes, completes (`Succeeded`), and moves `vm6` to a new node:
+
[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm6 -n {user}-troubleshoot-04
----
+
_Observation:_ Once the memory quota is increased to `6Gi`, the migration controller creates the target pod and completes the migration without requiring a VM restart. Compare the new `NODENAME` against Step 2 to confirm `vm6` migrated to a different node. (If the migration does not resume automatically, re-run `virtctl migrate vm6 -n {user}-troubleshoot-04`).
+
.Terminal output confirming `vmim` reached `Succeeded` and `vm6` moved to a new node
image::vm6-2-sol.png[Terminal output of oc get vmim and oc get vmi vm6 showing Succeeded migration on a new node, align="center"]

== Solution for Task 2: Troubleshooting Failure Scenario B

==== Guided Investigation & Root Cause Analysis

. Verify that `vm7` is in a `Running` state (the `migration-quota` from Task 1 may have previously blocked its initial pod from starting):
+
[source,sh,subs="attributes+"]
----
oc get vm,vmi vm7 -n {user}-troubleshoot-04
----
+
[NOTE]
====
If `vm7` is still in `Starting` or `Pending` after Task 1, restart it with `virtctl restart vm7 -n {user}-troubleshoot-04` and wait until `oc get vmi vm7 -n {user}-troubleshoot-04` reports `Running` before continuing.
====

. Initiate a live migration for `vm7`:
+
[source,sh,subs="attributes+"]
----
virtctl migrate vm7 -n {user}-troubleshoot-04
----
+
_Observation:_ The migration transitions to `Migrating` and stalls indefinitely.

. Inspect the pods in the namespace to identify the target migration pod:
+
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04
----
+
_Observation:_ Two `virt-launcher-vm7` pods are present: the original `Running` source pod and a new target pod stuck in `Pending`.

. Describe the `Pending` target pod to view its scheduler events (replace `<pending-virt-launcher-vm7-pod>` with the pending pod name):
+
[source,sh,subs="attributes+"]
----
oc describe pod <pending-virt-launcher-vm7-pod> -n {user}-troubleshoot-04
----
+
_Observation:_ Look at the *Events* section at the bottom of the output. The Kubernetes scheduler logs a `FailedScheduling` warning:
+
[source,text]
----
Warning  FailedScheduling  ...  0/X nodes are available: X node(s) didn't match pod affinity rules.
----
+
.Terminal output showing `FailedScheduling` due to pod affinity rules
image::vm7-1-sol.png[Terminal output of oc describe pod showing FailedScheduling pod affinity warning, align="center"]

. *Root Cause Analysis (RCA):* The `vm7` specification defines a hard `requiredDuringSchedulingIgnoredDuringExecution` `podAffinity` rule forcing the VM to co-locate on the exact same node as a pod labeled `app: anchor`. Because live migration requires scheduling the target pod onto a *different* node, no other node can satisfy the affinity rule.

==== Step-by-Step Resolution

. Cancel the stuck live migration so the `Pending` target pod is cleaned up:
+
[source,sh,subs="attributes+"]
----
virtctl migrate-cancel vm7 -n {user}-troubleshoot-04
----
+
[TIP]
====
In the OpenShift Web Console, navigate to *Virtualization* → *VirtualMachines* → *vm7* → *Actions* → *Cancel Migration*.
====

. Patch `vm7` to remove the `spec.template.spec.affinity` block:
+
[source,sh,subs="attributes+"]
----
oc patch vm vm7 -n {user}-troubleshoot-04 --type=merge -p '{"spec":{"template":{"spec":{"affinity":null}}}}'
----
+
[TIP]
====
Alternatively, run `oc edit vm vm7 -n {user}-troubleshoot-04` (or open *Virtualization* → *VirtualMachines* → *vm7* → *YAML* in the Web Console) and delete the entire `affinity` block under `spec.template.spec`.
====

. Confirm that the affinity rule has been cleared from the active VMI spec (no restart is required):
+
[source,sh,subs="attributes+"]
----
oc get vmi vm7 -n {user}-troubleshoot-04 -o jsonpath='{.spec.affinity}{"\n"}'
----
+
_Observation:_ The command returns an empty line.

. Trigger a new live migration and verify that it succeeds and moves `vm7` to another node:
+
[source,sh,subs="attributes+"]
----
virtctl migrate vm7 -n {user}-troubleshoot-04
oc get vmim -n {user}-troubleshoot-04
oc get vmi vm7 -n {user}-troubleshoot-04
----
+
_Observation:_ With the strict pod affinity rule removed, the scheduler places the target pod on an available worker node, the `VirtualMachineInstanceMigration` reaches `Succeeded`, and `vm7` runs smoothly on the destination node.
+
.Terminal output confirming `vm7` live migration `Succeeded` on a new node
image::vm7-2-sol.png[Terminal output of oc get vmim and oc get vmi vm7 showing Succeeded migration on a different node, align="center"]
