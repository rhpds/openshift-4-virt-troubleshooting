== Solution for Task 1: Troubleshooting Failure Scenario A

==== Guided Investigation & Root Cause Analysis

. Check the status of the Virtual Machine Instance:
+
[source,sh,subs="attributes+"]
----
oc get vmi vm3 -n {user}-troubleshoot-02
----
+
_Observation:_ The VMI remains stuck in the `Scheduling` or `Pending` phase and never enters `Running`.

. Locate the active `virt-launcher` pod in the target namespace:
+
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-02
----

. Describe the `virt-launcher` pod to check its status fields (replace `<virt-launcher-pod-name>` with the pod ID returned from the previous command):
+
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod-name> -n {user}-troubleshoot-02
----
+
_Observation:_ Look at the *Events* log at the bottom of the output. You will find a `FailedCreatePodSandBox` warning stating `failed to create bridge "enp2s0": "enp2s0" already exists but is not a bridge`.
+
.Pod events showing `FailedCreatePodSandBox` due to invalid bridge `enp2s0`
image::vm3-1-sol.png[Terminal output of oc describe pod showing Multus failed to create bridge enp2s0 event, align="center"]

. Inspect the `NetworkAttachmentDefinition` configuration in the namespace:
+
[source,sh,subs="attributes+"]
----
oc get net-attach-def vm-private-net -n {user}-troubleshoot-02 -o yaml
----

. *Root Cause Analysis (RCA):* The `NetworkAttachmentDefinition` (`vm-private-net`) is misconfigured to attach the secondary network interface to a physical network interface card (`enp2s0`) instead of the host's configured Linux bridge (`br0`). Because `enp2s0` is already a physical device, the CNI bridge plugin fails to create the pod sandbox.

==== Step-by-Step Resolution

. Patch the `vm-private-net` `NetworkAttachmentDefinition` so `spec.config` points to the `br0` Linux bridge instead of `enp2s0`:
+
[source,sh,subs="attributes+"]
----
oc patch net-attach-def vm-private-net -n {user}-troubleshoot-02 --type='merge' -p '{"spec":{"config":"{\"cniVersion\":\"0.3.1\",\"name\":\"vm-private-net\",\"type\":\"bridge\",\"bridge\":\"br0\",\"ipam\":{}}"}}'
----

. Verify that the VMI phase successfully transitions to `Running`:
+
[source,sh,subs="attributes+"]
----
oc get vmi vm3 -n {user}-troubleshoot-02
----
+
.Terminal output confirming `vm3` is in the `Running` phase
image::vm3-2-sol.png[Terminal output of oc get vmi vm3 showing Phase as Running and Ready as True, align="center"]

== Solution for Task 2: Troubleshooting Failure Scenario B

==== Guided Investigation & Root Cause Analysis

. Check the high-level operational state of the VM and VMI:
+
[source,sh,subs="attributes+"]
----
oc get vm,vmi vm4 -n {user}-troubleshoot-02
----
+
_Observation:_ `vm4` is `Running` with `READY=True` and has an assigned internal IP address.

. Verify that the web server inside the Guest OS is running and listening on port `8080` by connecting to the VM console (`cloud-user` / `password123`):
+
[source,sh,subs="attributes+"]
----
virtctl console vm4 -n {user}-troubleshoot-02
----
+
[source,sh]
----
curl -s http://localhost:8080
----
+
_Observation:_ The local request returns `Hello from vm4 web service!`, confirming the web application inside `vm4` is healthy. Exit the console using `Ctrl+]`.

. Test external access through the OpenShift `Route` (`vm4-web-route`):
+
[source,sh,subs="attributes+"]
----
ROUTE_URL=$(oc get route vm4-web-route -n {user}-troubleshoot-02 -o jsonpath='{.spec.host}')
curl -i http://$ROUTE_URL
----
+
_Observation:_ The router returns `HTTP/1.1 503 Service Unavailable` (`Application is not available`).

. Inspect the `Route`, `Service`, and `Endpoints` objects in the target namespace:
+
[source,sh,subs="attributes+"]
----
oc get route,svc,endpoints -n {user}-troubleshoot-02
----
+
_Observation:_ `vm4-web-route` points to `vm4-web-svc`, but the `ENDPOINTS` column for `vm4-web-svc` displays `<none>`.

. Describe the `Service` and check the labels on the `virt-launcher` pod to find why no endpoints are bound:
+
[source,sh,subs="attributes+"]
----
oc describe svc vm4-web-svc -n {user}-troubleshoot-02
oc get pods -n {user}-troubleshoot-02 --show-labels
----
+
_Observation:_ Look closely at the `Selector` field of `vm4-web-svc` (`app=vm4-web`) compared to the `Labels` on the `virt-launcher-vm4` pod (`app=vm4-app`).
+
.Terminal output showing empty `Endpoints` and mismatched `app` labels
image::vm4-1-sol.png[Terminal output showing empty Endpoints for vm4-web-svc and app=vm4-app label on pod, align="center"]

. *Root Cause Analysis (RCA):* The `vm4-web-svc` `Service` selects pods with the label `app=vm4-web`, whereas the `virt-launcher-vm4` pod carries the label `app=vm4-app` (inherited from `vm4`'s `spec.template.metadata.labels`). Because the selector does not match any running pod labels, Kubernetes never populates an `Endpoint` IP for `vm4-web-svc`, causing the OpenShift Router to return `503 Service Unavailable`.

==== Step-by-Step Resolution

. Patch `vm4-web-svc` so its label selector matches `app: vm4-app`:
+
[source,sh,subs="attributes+"]
----
oc patch svc vm4-web-svc -n {user}-troubleshoot-02 --type=merge -p '{"spec":{"selector":{"app":"vm4-app"}}}'
----

. Verify that `vm4-web-svc` now resolves a valid `Endpoint` IP address matching `vm4`:
+
[source,sh,subs="attributes+"]
----
oc get endpoints vm4-web-svc -n {user}-troubleshoot-02
----

. Re-test external access through `vm4-web-route` to confirm the web page loads successfully:
+
[source,sh,subs="attributes+"]
----
ROUTE_URL=$(oc get route vm4-web-route -n {user}-troubleshoot-02 -o jsonpath='{.spec.host}')
curl -i http://$ROUTE_URL
----
+
.Terminal output confirming `Endpoints` populated and `Route` returning `200 OK`
image::vm4-2-sol.png[Terminal output showing populated Endpoints and HTTP 200 OK response from vm4-web-route, align="center"]
