== Task 1 Solution: CNI and Network Attachment (Layer 2 Fault)

=== Step 1: Identify the CNI Failure
Check the events of the failing virt-launcher pod for `vm3` to discover why it cannot start.

[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-02
----

[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-vm3-pod> -n {user}-troubleshoot-02
----

*Diagnostic finding:* At the bottom of the output, you will see a Multus network warning similar to: `Warning FailedCreatePodSandBox …​ failed to create bridge "enp2s0": "enp2s0" already exists but is not a bridge.` This indicates the NetworkAttachmentDefinition is pointing to a physical network interface card instead of the required Linux bridge.

=== Step 2: Fix the NetworkAttachmentDefinition
Edit the broken NetworkAttachmentDefinition to point to the correct bridge.

[source,sh,subs="attributes+"]
----
oc edit net-attach-def vm-private-net -n {user}-troubleshoot-02
----
*(Alternatively, in the OpenShift Web Console: Navigate to Networking → NetworkAttachmentDefinitions → vm-private-net → YAML tab).*

. Locate the JSON config block and change `"bridge":"enp2s0"` to `"bridge":"br0"`.
. Save the changes. The CNI plugin will immediately re-attempt the connection, successfully attach to `br0`, and `vm3` will boot into a `Running` state.

== Task 2 Solution: Scheduling and Cloud-Init (Double Fault)

=== Step 1: Identify the Hardware Binding Error
Check the VM events for `vm4` to find the crash-loop failure. The virt-launcher pod is repeatedly deleted, so `oc describe pod` may fail with NotFound.

[source,sh,subs="attributes+"]
----
oc get vm vm4 -n {user}-troubleshoot-02
----

[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-02 --field-selector involvedObject.name=vm4
----

*Diagnostic finding:* You will see repeated VM events: `Warning SyncFailed server error. command SyncVMI failed: "failed to create SR-IOV hostdevices: failed to create PCI address pool with network status from file: context deadline exceeded: file is not populated with network-info"`, followed by `Stopped The VirtualMachineInstance crashed.`

=== Step 2: Fix the Interface Hardware Type
_Note: You must fix this in the YAML tab because the UI Network Interfaces tab will auto-correct it for you, bypassing the learning objective._

. In the Web Console, navigate to *Virtualization* → *VirtualMachines* and click on *vm4*.
. Click directly on the *YAML* tab.
. Scroll down to `spec.template.spec.domain.devices.interfaces`.
. Delete `sriov: {}` and type `bridge: {}` in its place.
. Click *Save*. 
. Click the *Actions* dropdown at the top right and select *Restart* to apply the hardware change. The pod will now successfully get scheduled and `vm4` will boot up.

=== Step 3: Discover the Layer 3 Typo (The Illusion of Success)
The VM is now running, but it has a hidden Layer 3 routing issue.

. Click the *Console* tab for *vm4* in the OpenShift UI.
. Log into the Guest OS (Username: `cloud-user`, Password: `password123`).
. Find your dynamically assigned IP address on `eth1`:
+
[source,sh,subs="attributes+"]
----
ip a show eth1
----
. Ping your own IP address (e.g., `ping -c 2 10.10.10.132`). It will succeed, creating the illusion that the network is fully functional. 
. Now, attempt to ping the gateway of that network:
+
[source,sh,subs="attributes+"]
----
ping -c 2 10.10.10.1
----

*Diagnostic finding:* The ping instantly fails with `connect: Network is unreachable`. Check your routing table (`ip route`). You will notice there is no route for the `10.10.10.0` network because `eth1` is configured with a `/32` mask. This mathematically isolates the VM.

=== Step 4: Correct the Cloud-Init Injection & Verify
Fix the subnet mask injected by Cloud-Init and perform a hard stop/start to apply it.

. In the Web Console, navigate to the *YAML* tab for *vm4*. *(Do not use the Scripts tab, as it may hide network data).*
. Scroll down to the `spec.template.spec.volumes` section and locate the `cloudInitNoCloud` block.
. Under `networkData`, change the address line from `/32` to `/24`. *Do not change the dynamically generated IP address itself*, only the mask suffix:
+
[source,yaml]
----
                  ethernets:
                    eth1:
                      addresses:
                      - 10.10.10.X/24
----
. Click *Save*.
. For Cloud-Init hardware network changes to take effect, a simple reboot is not enough. Click the *Actions* dropdown at the top right and select *Stop*. Wait for it to fully stop, then select *Start*.
. Once booted, open the *Console* and test the gateway ping again:
+
[source,sh,subs="attributes+"]
----
ping -c 2 10.10.10.1
----

*Verification Success:* The output will now change to `From 10.10.10.X icmp_seq=1 Destination Host Unreachable`. This error shift proves your Layer 3 routing is completely fixed and the VM successfully pushed the packet out onto the Linux Bridge. It only fails because the gateway itself does not physically exist on this isolated bridge.
