== Tasks

=== Task 1: Troubleshooting Quota-Blocked Migrations (The Silent Failure)

==== Problem Scenario

- A Virtual Machine `vm6` is deployed in namespace `{user}-troubleshoot-04`.
- The VM appears completely healthy and ready. However, when an administrator attempts to Live Migrate it, the migration gets stuck and never completes.
- Your tenant user has been granted a custom RBAC role (`quota-admin`) to manage resource limits in this specific namespace.

==== Diagnostic Steps

1. Navigate to *Virtualization -> VirtualMachines* in the OpenShift Web Console.
2. Ensure your Project is set to `{user}-troubleshoot-04`.
3. Click on `vm6`. On the *Overview* tab, note that there are no warnings.
4. Click the *Actions* dropdown and select *Migrate*.
5. The status will change to `Preparing for migration` but will fail to progress.
6. To find out why, navigate to *Workloads -> Pods*. Notice that no target migration pod (`virt-launcher-vm6-...`) is spinning up.
7. Click the *Events* tab for the namespace. You will see a `FailedCreate` error stating: `forbidden: exceeded quota: migration-quota`. Live Migration requires spinning up a second pod temporarily, and the namespace lacks the memory quota to allow it.

==== Goal
Using your delegated `quota-admin` permissions, resolve the `ResourceQuota` limitation so that the pending migration automatically resumes and completes.

=== Task 2: Troubleshooting Scheduling Conflicts (The Stuck Target Pod)

[NOTE]
====
You must complete Task 1 and resolve the namespace `ResourceQuota` issue before attempting this task. If the quota is not updated, `vm7`'s migration will also be blocked by the quota, hiding the scheduling error.
====

==== Problem Scenario

- A Virtual Machine `vm7` is deployed in namespace `{user}-troubleshoot-04`.
- A developer applied strict Pod Affinity rules to keep the VM on the same node as a specific anchor pod. When an administrator attempts to Live Migrate the VM, the UI accepts the command, but the migration gets permanently stuck in a `Migrating` state.

==== Diagnostic Steps

1. Navigate to *Virtualization -> VirtualMachines* in the OpenShift Web Console and click on `vm7`.
2. Click *Actions -> Migrate*. The VM will enter the `Migrating` state but will not progress.
3. Navigate to *Workloads -> Pods* in the `{user}-troubleshoot-04` namespace.
4. Locate the new target pod named `virt-launcher-vm7-...` and notice its status is stuck in `Pending`.
5. Click on the `Pending` pod and go to its *Events* tab.
6. Investigate the events to determine why the Kubernetes scheduler refuses to place this workload on another node (you will see a `FailedScheduling` warning due to a pod affinity/anti-affinity conflict).

==== Goal
Cancel the stuck migration, modify the VirtualMachine configuration to remove the strict scheduling constraints, and successfully complete the Live Migration.

=== Suggested Troubleshooting Commands

Check the status of VirtualMachines and VirtualMachineInstances in your namespace:
[source,sh,subs="attributes+"]
----
oc get vm -n {user}-troubleshoot-04
oc get vmi -n {user}-troubleshoot-04
----

Check the underlying virt-launcher pods (including any target migration pods stuck in `Pending`):
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04
----

View recent namespace events to catch quota rejections and scheduling warnings:
[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --sort-by='.lastTimestamp'
----

Inspect and modify the namespace `ResourceQuota`:
[source,sh,subs="attributes+"]
----
oc get resourcequota -n {user}-troubleshoot-04
oc describe resourcequota migration-quota -n {user}-troubleshoot-04
oc edit resourcequota migration-quota -n {user}-troubleshoot-04
----

Inspect a stuck target pod to view detailed scheduler errors:
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod> -n {user}-troubleshoot-04
----

Inspect or edit the VirtualMachine YAML configuration:
[source,sh,subs="attributes+"]
----
oc edit vm vm7 -n {user}-troubleshoot-04
----

Cancel or trigger a Live Migration from the CLI:
[source,sh,subs="attributes+"]
----
virtctl cancel-migration vm7 -n {user}-troubleshoot-04
virtctl migrate vm7 -n {user}-troubleshoot-04
----
