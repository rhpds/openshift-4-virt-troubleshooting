== Overview & Objectives

This lab focuses on diagnosing and resolving Virtual Machine live migration and scheduling issues in OpenShift Virtualization. By the end of this module, you will:

* Understand how OpenShift Virtualization orchestrates live migrations using target `virt-launcher` pods and `VirtualMachineInstanceMigration` (`vmim`) objects.
* Inspect namespace policies, cluster events, pod statuses, and VirtualMachine specifications to diagnose stalled migrations.

[NOTE]
====
This lab is designed to give you hands-on experience with real-world scenarios. We highly recommend exploring the errors, running the diagnostic commands, and trying to fix the issues on your own first—that is where the best learning happens!

If you get stuck or want to verify your findings, the companion *Guided Solution* is always available to help guide you through the next steps.
====

== Tasks

=== Task 1: Troubleshooting Failure Scenario A

==== Problem Scenario
A Virtual Machine named `vm6` is deployed in the namespace `{user}-troubleshoot-04`.

The VM appears completely healthy and ready. However, when attempting to Live Migrate it, the migration process stalls in a preparing state and never completes.

Run the following commands to initiate a migration and check the current status of `vm6` and its migration object:
[source,sh,subs="attributes+"]
----
virtctl migrate vm6 -n {user}-troubleshoot-04
oc get vm,vmim -n {user}-troubleshoot-04
----

The terminal output should look similar to this:

.Terminal output confirming `vm6` is stuck in `Preparing for migration`
image::vm6-1.png[Terminal output of oc get vm and vmim showing vm6 stuck in Preparing for migration, align="center"]

==== Reference Documentation
* Consult the Red Hat documentation on link:https://redhat.com[About live migration^].

==== Goal
Investigate the cluster events and namespace configuration, determine why the migration workload cannot initialize, implement a fix using your tenant permissions, and ensure `vm6` completes its Live Migration to another node.

=== Task 2: Troubleshooting Failure Scenario B

==== Problem Scenario
A Virtual Machine named `vm7` is deployed in the namespace `{user}-troubleshoot-04`.

When attempting to Live Migrate `vm7` (ensure it is in a `Running` state first), the migration request is accepted and enters a `Migrating` state, but it never progresses or moves to another node.

Run the following commands to initiate a migration and check the pods in your namespace:
[source,sh,subs="attributes+"]
----
virtctl migrate vm7 -n {user}-troubleshoot-04
oc get pods -n {user}-troubleshoot-04
----

The terminal output should look similar to this:

.Terminal output showing the target `virt-launcher-vm7` pod stuck in `Pending`
image::vm7-1.png[Terminal output of oc get pods showing running source pod and Pending target virt-launcher-vm7 pod, align="center"]

==== Reference Documentation
* Consult the Red Hat documentation on link:https://redhat.com[Controlling pod placement on nodes using scheduling rules^].

==== Goal
Investigate the stuck target pod and VirtualMachine definition, cancel the stalled migration, resolve the scheduling conflict, and successfully complete the Live Migration of `vm7`.

== Suggested Troubleshooting Reference Workflow

Use the following commands in sequence to analyze the state of either Virtual Machine (`vm6` or `vm7`) and isolate the root cause of the migration failures:

Check high-level VM and VMI states (including current node placement):
[source,sh,subs="attributes+"]
----
oc get vm,vmi -n {user}-troubleshoot-04
----

Check active `VirtualMachineInstanceMigration` objects:
[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
----

Locate underlying `virt-launcher` pods (including any target migration pods):
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04
----

Inspect a specific pod configuration and events (replace `<virt-launcher-pod>` with the pod ID found above):
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod> -n {user}-troubleshoot-04
----

Inspect the VirtualMachine specification:
[source,sh,subs="attributes+"]
----
oc describe vm <vm-name> -n {user}-troubleshoot-04
----

Check namespace policies and resource limits:
[source,sh,subs="attributes+"]
----
oc get resourcequota,limitrange -n {user}-troubleshoot-04
----

Query cluster events sorted chronologically:
[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --sort-by='.lastTimestamp'
----
