== Overview & Objectives

This lab focuses on diagnosing and resolving Virtual Machine Live Migration failures in OpenShift Virtualization. By the end of this module, you will:

- Understand how namespace `ResourceQuotas` impact the temporary target pods required for Live Migration.
- Use delegated RBAC roles to perform tenant-level remediation of resource limits.
- Troubleshoot stuck migrations caused by strict Kubernetes Pod Affinity and scheduling rules.

[NOTE]
====
This lab is designed to give you hands-on experience with real-world scenarios. We highly recommend exploring the errors, running the diagnostic commands, and trying to fix the issues on your own first—that is where the best learning happens! 

If you get stuck or want to verify your findings, the companion *Guided Solution* is always available to help guide you through the next steps.
====

== Tasks

=== Task 1: Troubleshooting Quota-Blocked Migrations (The Silent Failure)

==== Problem Scenario
A Virtual Machine named `vm6` is deployed in the namespace `{user}-troubleshoot-04`. The VM appears completely healthy and ready. However, when you attempt to Live Migrate it, the migration gets stuck and never completes.

Your tenant user has been granted a custom RBAC role (`quota-admin`) to manage resource limits in this specific namespace.

==== Reference Documentation & Setup
- Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/virtualization/live_migration#virt-about-live-migration[About live migration^] to understand the temporary pod requirements.
- Review Kubernetes documentation on link:https://kubernetes.io/docs/concepts/policy/resource-quotas/[Resource Quotas^].

==== Goal
Investigate the namespace events to determine exactly why the Live Migration is failing to progress. Using your delegated `quota-admin` permissions, resolve the underlying cluster configuration issue so that the pending migration automatically resumes and successfully completes.

=== Task 2: Troubleshooting Scheduling Conflicts (The Stuck Target Pod)

*Note: You must successfully complete Task 1 and resolve the namespace `ResourceQuota` issue before attempting this task. While the quota exists it blocks `vm7`'s initial virt-launcher pod, so `vm7` cannot start at all and there is no migration to troubleshoot.*

==== Problem Scenario
A Virtual Machine named `vm7` is deployed in namespace `{user}-troubleshoot-04`. A developer applied strict Pod Affinity rules to keep the VM on the same node as a specific anchor pod.

Because the `migration-quota` from Task 1 also blocks this VM's first virt-launcher pod, `vm7` remains in `Starting` until the quota is removed. The VMI exists but stays `Pending`, and no virt-launcher pod is created because quota admission rejects it. After completing Task 1, confirm `vm7` is `Running`. If it is still `Starting`, restart it with `virtctl restart vm7 -n {user}-troubleshoot-04` and wait for it to reach `Running`.

When you attempt to Live Migrate the running VM, the UI accepts the command, but the migration gets permanently stuck in a `Migrating` state.

==== Reference Documentation & Setup
- Consult the Red Hat documentation on link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/nodes/scheduling-pods-using-affinity-anti-affinity[Scheduling pods using affinity and anti-affinity^].

==== Goal
Attempt to Live Migrate `vm7` and identify the stuck target pod. Investigate the Kubernetes scheduler events to understand the pod affinity conflict preventing the migration. Modify the VirtualMachine configuration to remove the strict scheduling constraints, then re-initiate and successfully complete the Live Migration.

== Suggested Troubleshooting Reference Workflow

Use the following commands to navigate the cluster objects, inspect namespace events, and verify scheduling constraints.

Start a live migration (replace `<vm-name>` with `vm6` or `vm7`):
[source,sh,subs="attributes+"]
----
virtctl migrate <vm-name> -n {user}-troubleshoot-04
----

Check the high-level VM and VMI states in your namespace:
[source,sh,subs="attributes+"]
----
oc get vm -n {user}-troubleshoot-04
oc get vmi -n {user}-troubleshoot-04
----

Check the live migration objects:
[source,sh,subs="attributes+"]
----
oc get vmim -n {user}-troubleshoot-04
----

Identify the underlying virt-launcher pods (look for target migration pods stuck in a Pending state):
[source,sh,subs="attributes+"]
----
oc get pods -n {user}-troubleshoot-04
----

Query the namespace events to uncover silent API rejections (crucial for finding quota blocks):
[source,sh,subs="attributes+"]
----
oc get events -n {user}-troubleshoot-04 --sort-by='.lastTimestamp' | grep -i -E 'FailedCreate|quota'
----

Inspect the ResourceQuotas applied to your namespace:
[source,sh,subs="attributes+"]
----
oc get resourcequota -n {user}-troubleshoot-04
----

Describe a specific stuck virt-launcher pod to uncover scheduling conflicts (replace `<virt-launcher-pod>` with the target pod name):
[source,sh,subs="attributes+"]
----
oc describe pod <virt-launcher-pod> -n {user}-troubleshoot-04
----

Review and edit the VM configuration to fix affinity and scheduling errors:
[source,sh,subs="attributes+"]
----
oc edit vm vm7 -n {user}-troubleshoot-04
----
