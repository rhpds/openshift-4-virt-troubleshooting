== Solution for Task 1: Troubleshooting Failure Scenario A

==== Guided Investigation & Root Cause Analysis

. Check the status of the Virtual Machine Instance:
+
[source,sh]
----
oc get vmi vm1 -n {user}-troubleshoot-01
----
_Observation:_ The VMI remains stuck in the `Scheduling` or `Pending` phase and never enters `Running`.

. Locate and describe the active `virt-launcher` pod:
+
[source,sh]
----
oc get pods -n {user}-troubleshoot-01
oc describe pod <virt-launcher-pod-name> -n {user}-troubleshoot-01
----

. Scroll down to the *Events* log at the bottom of the pod description. 
+
_Observation:_ You will find `ErrImagePull` and `ImagePullBackOff` status codes.

. *Root Cause Analysis (RCA):* The OpenShift cluster nodes are unable to pull the container disk image because the target image resides inside a secured, private image registry, and no matching authentication credentials (pull secrets) exist in the `{user}-troubleshoot-01` namespace.

==== Step-by-Step Resolution

. Create a Docker registry secret containing the authentication credentials for the secure registry (using the Quay variables provided):
+
[source,sh]
----
oc create secret docker-registry registry-secret \
  --docker-server={quay_url} \
  --docker-username={quay_user} \
  --docker-password={quay_password} \
  -n {user}-troubleshoot-01
----

. Link the pull secret to the default ServiceAccount so the pod template can implicitly use it:
+
[source,sh]
----
oc secrets link default registry-secret --for=pull -n {user}-troubleshoot-01
----

. Stop and restart the virtual machine to trigger a fresh pod deployment cycle:
+
[source,sh]
----
oc virt stop vm1 -n {user}-troubleshoot-01
oc virt start vm1 -n {user}-troubleshoot-01
----

. Verify that the VMI phase updates successfully to `Running`.

=== Solution for Task 2: Troubleshooting Failure Scenario B

==== Guided Investigation & Root Cause Analysis

. Confirm that the VM is failing to scale up:
+
[source,sh]
----
oc get vm vm2 -n {user}-troubleshoot-01
oc get vmi vm2 -n {user}-troubleshoot-01
----

. Inspect the cluster events filtered specifically for the `vm2` resource architecture:
+
[source,sh]
----
oc get events -n {user}-troubleshoot-01 --sort-by='.metadata.creationTimestamp'
----

. Inspect the underlying XML/spec configuration template embedded within the VM definition:
+
[source,sh]
----
oc get vm vm2 -o yaml -n {user}-troubleshoot-01
----
Look closely at the `spec.template.spec.volumes` array, specifically items mapping to `cloudInitNoCloud`. Notice that it references a secret named `user-credentials`.

. *Root Cause Analysis (RCA):* The `vm2` configuration requires custom instance initialization parameters via Cloud-Init, which references an Opaque Secret named `user-credentials`. The VM cannot boot because this dependency is missing from the namespace.

==== Step-by-Step Resolution

. Generate the missing `user-credentials` secret manifest containing the mandatory `#cloud-config` fields:
+
[source,sh]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: user-credentials
  namespace: {user}-troubleshoot-01
type: Opaque
stringData:
  userdata: |
    #cloud-config
    user: admin
    password: PasswordSecure99
    chpasswd: { expire: False }
EOF
----

. Restart the VM to force the control loop to clear the dependency error:
+
[source,sh]
----
oc virt stop vm2 -n {user}-troubleshoot-01
oc virt start vm2 -n {user}-troubleshoot-01
----

. Verify the operational state:
+
[source,sh]
----
oc get vmi vm2 -n {user}-troubleshoot-01
----
The status should now read `Running`.
